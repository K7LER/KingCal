  Final Score: 3.4 / 5.0 — FAIR

  ---
  Executive Summary

  KingCalendar is a mature, feature-rich VCL component library that has been responsibly maintained through three
  decades of Delphi evolution. The recent March 2026 modernization (VCL Styles, High DPI scaling, System.DateUtils
  adoption) demonstrates disciplined, incremental improvement.

  The primary technical debt comes from the original 1995 architecture: a monolithic core class (TKingCalendar at ~2,488
   lines), pervasive code duplication across spin/dialog units, and a legacy database component (DBKing.pas) that won't
  compile in modern Delphi. Several bugs were identified that should be addressed promptly.

  ---
  Critical Points

  1. [CRITICAL] DBKing.pas will not compile — Uses legacy BDE-era units (WinTypes, WinProcs, DBTables, DBIErrs).
  Currently excluded from build but remains in source tree.
  2. [CRITICAL] Memory corruption in Caledit.pas — The design-time editor frees TFont objects that belong to the
  component's internal state (frees TitleFont reference directly instead of using Assign).
  3. [WARNING] Hard cast TForm(AOwner) in 12+ constructors will crash if the owner is a TFrame or TDataModule.
  4. [WARNING] Global FormatSettings mutation in 6+ units silently overwrites the host application's locale settings.
  5. [WARNING] Massive code duplication — GetMinHeight, SetEditRect, CreateParams, KeyPress/IsValidChar duplicated 4-5
  times across spin/dialog units.
  6. [WARNING] Application.ProcessMessages called unnecessarily in TKingNavigator — potential re-entrancy bugs.
  7. [RECOMMENDATION] TKingCalendar.IsLeapYear method name shadows System.SysUtils.IsLeapYear — fragile name resolution.

  ---
  Dimension-by-Dimension Analysis

  Architecture (3/5 — Acceptable)

  - Clean runtime/design-time package split across all 6 Delphi versions
  - Companion controls use proper Notification mechanism for lifetime management
  - TKingCalendar is a God Class (~50 fields, 60+ methods) handling rendering, date logic, events, cell text, colors,
  and DPI scaling
  - KingTool.pas bundles many unrelated control classes (2,768 lines)
  - Hook mechanism is a fixed-size array (TKingHooks = array[1..20]) with no unsubscribe

  Clean Code (4/5 — Good)

  - Consistent comment style (// LR20260323 - ...) throughout
  - MIT license headers on every unit
  - Fully qualified unit names used consistently
  - Some naming inconsistencies: eDayChange vs TKingColoring, fUseDay vs FDate, nextMonth vs SetMonth
  - with statement used in Paint methods (discouraged in modern Delphi)

  Code Smells (3/5 — Acceptable)

  - 5 copies of GetMinHeight across spin/dialog units
  - Paint method ~310 lines with deeply nested local procedures
  - DoVisualEdit in Kccmpedt.pas — 90 lines of repetitive property copying

  SOLID (3/5 — Acceptable)

  - SRP violated by TKingCalendar and KingTool.pas
  - OCP violated by ColorSet1..ColorSet9 individual properties
  - LSP generally respected — appropriate inheritance hierarchy
  - No interfaces defined (ISP/DIP not applicable for this component type)

  Memory Management (4/5 — Good)

  - TKingCalendar.Destroy properly cleans up all owned objects with FreeAndNil
  - TKingPopup.Execute uses correct try..finally
  - Bug: Caledit.pas frees component-owned TFont objects directly

  Security (4/5 — Good)

  - Minimal attack surface (no network, file I/O, or SQL)
  - Only concern: global FormatSettings mutation affecting host applications

  ---
  Conclusion

  KingCalendar is well-suited for continued use and incremental modernization. The most urgent items — the TFont memory
  corruption, unsafe TForm(AOwner) casts, and global FormatSettings mutations — can be addressed quickly and would
  immediately improve reliability. The recommended short/medium-term actions would bring the codebase to a Good (4.0+)
  rating with manageable effort.
